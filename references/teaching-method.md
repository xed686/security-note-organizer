# 讲解方法:怎么把安全知识讲给真正的小白

本文件回答一个问题:同一个知识点,怎样写才能让没有基础的人**真的听懂**,并且**用得出来**。

## 目录
1. 费曼式写作的五条规则

## 1. 费曼式写作的五条规则

1. **假设读者聪明但零基础**。不说"显然""众所周知",不假设他知道缩写。
2. **先结论,后细节**。每个小节开头一句话讲清这节要解决什么。
3. **一个概念只引入一次,马上讲清**。术语保留英文原词(如 Payload、Web Shell),第一次出现时用中文把含义讲透,之后直接用。
4. **能用类比就先类比,再落到技术**。类比负责建立画面,技术描述负责精确,两者都要有。
5. **讲完要能复述**。写完一个知识点,自问:一个初学者合上笔记,能否用自己的话讲出"它是什么、为什么、怎么做"?讲不出来就是没写透。

## 2. 每一步都要有 why:三问法

渗透测试里的每一个动作都是为了回答某个问题,或排除某种可能。笔记里每个步骤固定回答:

| 三问 | 要写清的内容 |
|---|---|
| 做什么 | 具体动作,足够具体到能照着做 |
| 为什么这么做 | 这一步的目的:在验证什么假设、排除什么可能、为下一步准备什么 |
| 得到什么 | 预期现象;**没得到预期时说明什么**,下一步怎么调整 |

例:讲 SQL Injection 里"先在参数后面加一个单引号"。

- 做什么:在参数值后追加 `'`。
- 为什么:单引号是 SQL 字符串的边界符。如果输入被直接拼进查询,多出的引号会让语句语法出错,这是在**探测"用户输入有没有被当成代码的一部分"**。
- 得到什么:页面报错或返回异常,说明输入进入了 SQL 语句,值得继续;页面毫无变化,不代表没有注入,可能是错误被屏蔽,要换盲注思路验证。

只写"加单引号看有没有报错"是错误示范,小白学完仍然不知道**为什么**,换一个场景就不会用了。

## 3. 讲原理:从 root cause 出发

漏洞的本质往往是同一类错误:**程序把"数据"当成了"指令"**,或**信任了不该信任的东西**。讲原理时按这条线走:

1. 正常情况下程序是怎么工作的(正常流程)。
2. 开发者在哪里做了什么假设(例如"用户只会输入数字")。
3. 攻击者如何打破这个假设。
4. 因此产生了什么后果。

读者掌握了 root cause,才可能在没见过的场景里认出同一类问题。这是"漏洞直觉"的来源,也是笔记中最值得花篇幅的部分。

## 4. 拆解命令和 payload

任何命令、参数、payload 都要拆开讲。格式:

| 片段 | 作用 | 为什么需要 |
|---|---|---|

并补三件事:

- **正常输出长什么样**,关键信息在哪一行。
- **哪些参数是必须的,哪些可以按场景改**,改的依据是什么。
- **这条命令在整个流程里的位置**:它的输出会喂给下一步的哪里。

## 5. 类比怎么选

- 选读者日常能接触的东西:门禁、快递、银行柜台、餐厅点菜。
- 类比要**能映射到关键机制**,不能只是好玩。比如"SQL 拼接像把顾客口述的话直接抄进订单系统,顾客说'再加一单免费的',系统也照抄执行"。
- 讲完类比,明确指出**类比哪里和真实情况不同**,避免误导。

## 6. 把知识变成"漏洞直觉"

在"实战怎么用"一节,帮读者建立这三种能力:

- **触发线索**:看到什么特征应该想到这个漏洞(参数拼接、用户可控 URL、可上传的文件类型、版本号暴露……)。
- **最小验证**:用最小代价、最不破坏目标的方法确认假设。
- **决策分叉**:成立了做什么,不成立换什么思路。

同时尽量写出**同类问题的共同模式**,例如"凡是服务端替用户去访问某个地址,都要想到 SSRF",让读者能举一反三。

## 7. 常见写作坑

| 坑 | 为什么不好 | 改法 |
|---|---|---|
| 只罗列步骤,没有原因 | 读者只会背,换场景就用不了 | 每步补三问 |
| 术语堆叠,不解释 | 小白直接放弃 | 第一次出现讲透,保留英文原词 |
| 案例泛泛("某公司被攻击") | 不能联系业务 | 用可查证的真实事件,或明确标注的示例场景 |
| 把补充内容混进原笔记 | 读者无法核实 | 用"🔎 补充"标注块 |
| 写得很长但没有重点 | 淹没关键点 | 用相关度分级控制详略 |
| 每段都重复"仅限授权" | 打断阅读 | 在笔记开头写一次即可 |
